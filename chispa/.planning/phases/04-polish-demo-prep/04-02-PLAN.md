# Plan 02: Error States — All Four Failure Modes

## Objective

`useAnalysis.ts` currently handles errors generically: HTTP non-OK responses produce `"Error ${status}: ${text}"`, network failures forward the raw JS error message, and SSE `error` events forward the server's message verbatim. This plan adds specific handling for each of the four failure modes documented in CONTEXT.md, resulting in clean Spanish UI copy in every failure case, retry buttons where appropriate (429, network failure), and no retry button for timeout (user should refine their idea). The `App.tsx` error card is updated to show the retry button conditionally.

## Context

The `useAnalysis` hook returns `{ state, steps, result, error, submit, abort }`. The `error` field is `string | null`. The hook has an `'error'` state path already. `App.tsx` renders the error card when `displayState === 'error' && error`.

**Four failure modes:**

1. **Network failure** — `fetch()` throws (server unreachable, CORS, DNS). Currently: forwards `err.message` (often "Failed to fetch" — English, not polished). Fix: intercept in the catch block, produce Spanish copy.

2. **429** — `response.status === 429` before SSE starts. Currently: produces `"Error 429: Demasiados análisis en curso. Intenta en unos segundos."` (concatenated from template literal). Fix: explicit 429 check, canonical Spanish message, retry button.

3. **Claude timeout** — server sends `{ type: 'error', message: '...' }` SSE event. Currently: the message is forwarded verbatim from the server. This is acceptable IF the server sends Spanish. Verify the server's timeout message is the correct Spanish copy; if not, normalize it client-side.

4. **Malformed result JSON** — the `result` SSE event arrives but its `data` field fails validation. Currently: `msg.data` is assigned directly with no validation. Fix: add minimal shape check on `msg.data`; on failure, set Spanish error message and `'error'` state. If some data exists (partial result), keep it in `result` so the Dashboard can render what it has.

**Retry button:** `App.tsx` currently shows a generic message "Puedes intentar de nuevo con el formulario de arriba." after an error. For 429 and network failures, add a dedicated retry button that calls `submit` again with the last submitted idea. For timeout, keep the existing copy without a retry button.

**Hook return type must not change** — `{ state, steps, result, error, submit, abort }` stays the same. To support retry, App.tsx will cache the last submitted idea in its own state.

<action>
In `client/src/hooks/useAnalysis.ts`, find the SSE message handler for `msg.type === 'result'` (around lines 94-97):
```typescript
} else if (msg.type === 'result') {
  setResult(msg.data)
  setState('complete')
}
```

Replace with:
```typescript
} else if (msg.type === 'result') {
  // Validate minimal shape before accepting — Claude can return malformed JSON
  const data = msg.data
  if (!data || !data.verdict || !Array.isArray(data.competitors) || !Array.isArray(data.risks)) {
    // Keep whatever partial data exists; show error so user knows it's incomplete
    if (data) setResult(data)
    setError('Análisis incompleto. Los datos no están en el formato esperado.')
    setState('error')
  } else {
    setResult(data)
    setState('complete')
  }
}
```

This ensures that if Claude returns a `result` event with missing or structurally wrong data, the app shows an error instead of a blank/broken dashboard. If partial data exists, it is stored in `result` so the Dashboard can render what it has — this is the "partial results if available" behavior from CONTEXT.md.

No other changes to the hook.
